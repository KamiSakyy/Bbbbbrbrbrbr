# Архитектура и инженерные решения

Документ описывает, **почему** браузер сделан так, а не иначе. Здесь собраны решения, которые
влияют на скорость, вес APK, приватность и поведение в фоне.

---

## 1. Почему GeckoView, а не WebView и не Chromium из исходников

**Android WebView** — запрещён условиями задачи и технически не подходит: это чужой компонент,
который обновляется системой, не даёт доступа к блокировке на уровне сети и к управлению
процессами. Плюс версия движка на устройстве непредсказуема.

**Chromium из исходников** даёт Blink + V8, но:
- сборка занимает 4–10 часов на мощном раннере и требует 60–100 ГБ диска;
- публичного Android-дистрибутива CEF **не существует** (CEF официально поддерживает только
  Windows/macOS/Linux);
- для мобильного UI пришлось бы писать собственный слой поверх `//content` на C++/JNI — это
  недели работы, и каждая сборка — часы CI.

**GeckoView** — это готовый, поддерживаемый Android-дистрибутив независимого движка Gecko
(Mozilla) с Maven-артефактом и стабильным Java API. Он даёт всё, что нужно от «полноценного
браузера»: собственный JS-движок SpiderMonkey, многопоточный CSS (Stylo), GPU-рендеринг (WebRender),
изоляцию сайтов (Fission), блокировку контента, WebExtensions, приватные контексты и сериализацию
состояния сессии.

Итог: тот же класс технологий, что у Firefox для Android, но с нашим интерфейсом и нашими
оптимизациями.

## 2. Фоновый режим: как сайты выживают свёртывание

Три уровня защиты:

1. **Сессии живут в процессе, а не в Activity.** Движок поднимается в
   `YandexBrowserApp.onCreate()`, а `TabManager` создаётся там же. Поворот экрана или пересоздание
   Activity не трогают `GeckoSession` — вкладки не перезагружаются.
2. **Foreground-сервис.** Когда пользователь уходит из приложения (`onStop`), поднимается
   `KeepAliveService` с низкоприоритетным уведомлением. Android не убивает такой процесс, поэтому
   JS-таймеры, WebSocket'ы, медиа и загрузки продолжают работать.
3. **Сериализация состояния.** `ProgressDelegate.onSessionStateChange` отдаёт `SessionState`
   (история, скролл, формы) — он пишется на диск. Если система всё-таки выгрузит процесс,
   при следующем запуске сессия восстанавливается через `restoreState()`, и пользователь видит
   страницу на том же месте.

Дополнительно: `suspendMediaWhenInactive = false`, поэтому медиа в фоновой вкладке не глохнет.

Активной (visible) держится только текущая вкладка — так экономится память, а остальные сессии
остаются открытыми и не теряют состояние. Когда приложение возвращается на передний план,
сервис останавливается — висящего уведомления нет.

## 3. Экономия трафика: что именно экономит

Режим включён по умолчанию и состоит из четырёх слоёв:

| Слой | Что делает | Эффект |
|---|---|---|
| `ContentBlocking` движка | antiTracking `STRICT`, Safe Browsing, криптомайнинг, фингерпринтинг | не скачиваются скрипты трекеров |
| `cookieBehavior = ACCEPT_FIRST_PARTY` | сторонние cookie не принимаются | меньше запросов, меньше рекламы с таргетингом |
| `webFontsEnabled = false` | отключены веб-шрифты | десятки-сотни КБ на страницу |
| Встроенное расширение | собственный список рекламных доменов (`webRequest`, `blocking`) | реклама не загружается вообще |

Плюс `queryParameterStripping` — из ссылок вырезаются трекинговые параметры (`utm_*`, `gclid`, …).

Счётчики: каждое блокирование приходит в `ContentBlocking.Delegate.onContentBlocked` с
категорией. Количество блокировок — точная метрика. Сэкономленные байты — **оценка** по типу
заблокированного ресурса (в UI помечена знаком «≈»), потому что движок не отдаёт реальный вес
отменённого запроса.

Когда пользователь выключает экономию, расширение получает `config.blockAds = false` через
нативный порт и перестаёт блокировать; настройки движка, требующие пересоздания рантайма,
перечитываются при следующем запуске.

## 4. Тёмная тема: два механизма

1. **На уровне движка** — `preferredColorScheme = COLOR_SCHEME_DARK`. Это влияет на
   `prefers-color-scheme` и `color-scheme`, поэтому все сайты, у которых есть тёмная тема,
   переключаются на неё сами. Это ровно то, что просил заказчик: «у всех сайтов включать тёмную
   тему, если она у них есть».
2. **Расширение** — для сайтов, у которых тёмной темы нет. Логика такая: браузер уже сообщил
   странице, что предпочитает тёмное; если её фон всё равно светлый и в `<meta name="color-scheme">`
   нет `dark` — значит своей темы нет, и `darkmode.js` аккуратно инвертирует страницу
   (`filter: invert(1) hue-rotate(180deg)`), возвращая исходные цвета картинкам, видео,
   canvas и SVG. Класс вешается только после реальной проверки фона, поэтому сайты с собственной
   тёмной темой не трогаются вообще.

## 5. Вес APK: почему маленький UI при большом движке

Нативный движок Gecko (`libxul.so` + `omni.ja`) — это 88 МБ готового APK на arm64, и уменьшить его на стороне приложения нельзя: это и есть полноценный браузерный движок.
Всё остальное — сжимаем:

- R8 с полной обфускацией + `shrinkResources`;
- только локали `ru` и `en`;
- раздельные APK по ABI (arm64 / armeabi-v7a / x86_64) — каждый несёт один набор библиотек;
- сжатие нативных библиотек в APK (`useLegacyPackaging`) — минус ~95 МБ на arm64;
- собственный набор иконок (`ui/icons/BIcons.kt`) вместо `material-icons-extended` (~2 МБ);
- собственный загрузчик фавиконок с дисковым кэшем вместо Coil/Glide;
- собственные тост-бар, шторка меню, чипы и переключатели — без лишних зависимостей.

Исключения для R8 описаны в `app/proguard-rules.pro`: классы `org.mozilla.geckoview.**` и наши
делегаты не обфусцируются, потому что движок вызывает их через JNI/reflection.

## 6. Что осознанно не сделано в v1.0

- **Диалоги разрешений** (камера, микрофон, геолокация, уведомления). Сейчас движок не получает
  `PermissionDelegate`, поэтому запросы сайтов отклоняются по умолчанию — это безопасный, приватный
  дефолт. Диалоги с сохранением выбора — следующий шаг.
- **Своя система загрузок с куками**: сейчас используется системный `DownloadManager`
  (докачка, уведомления, работа в фоне) — но он не умеет отправлять куки сессии.
- **Синхронизация** закладок и вкладок между устройствами.
